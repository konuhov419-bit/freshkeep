# FreshKeep: документация backend (ДЗ 5)

## 1. Архитектура

```
Браузер (web/)  ──HTTPS/JSON──▶  REST API (server/, Node.js 22, без зависимостей)  ──▶  БД
  fetch + JWT в заголовке          маршруты, JWT, проверка владельца, CORS, логи         SQLite (migrations/)
```

| Компонент | Что делает |
|---|---|
| `web/` | Фронтенд (из ДЗ 4). Теперь работает с реальным API: вход и регистрация, загрузка и отправка данных, обработка ошибок 401/403/422/429/5xx и обрыва сети |
| `server/app.js` | HTTP-сервер и маршруты `/api/*`, раздача фронтенда, CORS, лимит попыток входа, журнал запросов |
| `server/auth.js` | Пароли: scrypt с солью. Токены: JWT HS256 на 7 дней. Проверка email и пароля |
| `server/db.js` | Подключение к БД и применение миграций `migrations/*.sql` по порядку, каждая в транзакции |
| `server/log.js` | Журнал в формате JSON (stdout и файл `logs/api.log`) |
| `migrations/` | SQL-схема: `users`, `products`, `shopping_items`, уникальный индекс против дублей |
| `supabase/` | Эквивалентная схема PostgreSQL с политиками RLS и скрипт проверки (см. п. 6) |

Валидация продукта и расчёт списания используют **один и тот же код** на клиенте и сервере (`web/src/domain/inventory.js`), поэтому правила не расходятся.

### Выбор решения (шаг 2)
Выбран **вариант B: собственный API (self-hosted)**. Причины: полный контроль над логикой (частичное списание, единицы, дубли), понятная отладка по собственным логам, одно приложение без внешних аккаунтов. Supabase удобнее для быстрого старта, и для него подготовлена схема с RLS (п. 6).

> **Отличия от задания (честно).** (1) В моей среде нет доступа к npm и запущенного Docker-демона, а для PostgreSQL нужен драйвер Node. Поэтому API работает на встроенном в Node 22 SQLite (`node:sqlite`, без зависимостей), а схема для PostgreSQL с RLS подготовлена и проверена отдельно на локальном PostgreSQL 16, но API к ней не подключён. (2) VPS не поднимался и приложение не публиковалось: нет доступа к вашим аккаунтам. (3) `Dockerfile` и `docker-compose.yml` написаны, но не запускались (нет демона Docker).

## 2. Модель данных

| Таблица | Поля | Связи и ограничения |
|---|---|---|
| `users` | id, email (уникальный), password_hash, created_at | — |
| `products` | id, user_id, name (1–100), quantity (> 0), unit (шт, г, кг, мл, л), storage (fridge, freezer, pantry), expires_at, created_at, updated_at | `user_id` → `users`, каскадное удаление; индекс (user_id, expires_at) |
| `shopping_items` | id, user_id, name, name_key, is_bought, created_at | `user_id` → `users`; уникальность (user_id, name_key) запрещает дубли без учёта регистра и лишних пробелов |

Проектирование с AI: требования из `technical_specification.md` (раздел «Модель данных») и `user_stories.md` (критерии US-02, US-10) переданы агенту, схема сгенерирована и скорректирована вручную: добавлены CHECK-ограничения, каскадное удаление, `name_key` и отдельная миграция 002 для уникального индекса. Семейный доступ (Household) оставлен вне этой версии: данные принадлежат одному пользователю.

## 3. Развёртывание

### Локально (проверено)
```bash
cd freshkeep
npm start            # http://localhost:5173 (нужен Node.js 22.5+, npm install не нужен)
npm test             # 32 теста
```
При первом запуске создаётся `.env` со случайным `JWT_SECRET` (файл в `.gitignore`). Миграции применяются автоматически.

### Переменные окружения (`.env.example`)
| Переменная | Назначение |
|---|---|
| `JWT_SECRET` | Секрет подписи токенов, минимум 32 символа. Без него сервер не стартует |
| `ALLOWED_ORIGIN` | Источники для CORS через запятую (`https://app.example.com`) или `*` |
| `PORT`, `DB_PATH`, `LOG_FILE` | Порт, путь к файлу БД, путь к журналу |

### Docker (не проверено, нет демона в среде разработки)
```bash
cp .env.example .env     # задайте JWT_SECRET
docker compose up -d --build
```
Данные и логи хранятся в томах, контейнер работает не от root, настроен healthcheck.

### Фронтенд на отдельном хостинге
В `web/config.js` укажите `globalThis.FRESHKEEP_API_URL = 'https://api.example.com'`, а в `ALLOWED_ORIGIN` на сервере адрес фронтенда.

## 4. API

Ошибки всегда в формате `{"error": {"code", "message", "fields?"}}`. Защищённые маршруты требуют заголовок `Authorization: Bearer <токен>`.

| Метод и путь | Описание | Коды |
|---|---|---|
| `GET /api/health` | Проверка работы | 200 |
| `POST /api/auth/register` | `{email, password}` → `{token, user}` | 201, 409, 422, 429 |
| `POST /api/auth/login` | то же | 200, 401, 429 |
| `GET /api/me` | Текущий пользователь | 200, 401 |
| `GET /api/products` | Продукты пользователя (по сроку) | 200, 401 |
| `POST /api/products` | `{name, quantity, unit, storage, expiresAt?}` | 201, 401, 422 |
| `PATCH /api/products/:id` | Частичное изменение полей | 200, 401, 403, 404, 422 |
| `POST /api/products/:id/consume` | `{amount, unit?}`, частичное списание; если съедено всё, запись удаляется | 200, 403, 404, 422 |
| `DELETE /api/products/:id` | Удаление | 204, 403, 404 |
| `GET/POST /api/shopping` | Список / добавление `{name}` | 200/201, 409, 422 |
| `PATCH /api/shopping/:id` | `{isBought: boolean}` | 200, 403, 404, 422 |
| `DELETE /api/shopping/:id` | Удаление | 204, 403, 404 |

## 5. Безопасность

| Мера | Реализация |
|---|---|
| Аутентификация | Регистрация и вход, JWT HS256 (7 дней), пароли хешируются scrypt с солью. Ответ при неверном email и неверном пароле одинаковый |
| Политики доступа | Каждый запрос к данным проверяет владельца: чужая запись даёт **403**, несуществующая **404**. Тест `изоляция данных` проверяет чтение, изменение, списание и удаление |
| RLS | Для PostgreSQL и Supabase: политики `user_id = auth.uid()` для select, insert, update, delete; `anon` доступа не имеет (п. 6) |
| CORS | Заголовок отдаётся только источникам из `ALLOWED_ORIGIN`; preflight `OPTIONS` отвечает 204 |
| Секреты | `JWT_SECRET` только из окружения или `.env` (в `.gitignore`), создаётся случайным; в репозитории только `.env.example` |
| Защита от перебора | Не более 10 попыток входа или регистрации в минуту с одного адреса, затем 429 с `Retry-After` |
| Прочее | Лимит тела запроса 100 КБ; экранирование вывода на клиенте (защита от XSS); заголовки `nosniff` и CSP; внутренние ошибки не раскрывают детали; пароли и токены не попадают в логи (есть тест) |

## 6. Схема PostgreSQL и RLS (проверено)
Файл `supabase/migrations/001_init.sql` содержит ту же модель данных для PostgreSQL с политиками RLS. Скрипт `bash supabase/test_rls.sh` поднимает временный PostgreSQL 16, применяет миграцию и проверяет изоляцию. Результат прогона:

```
миграция применена
A видит своих строк: 1
B видит строк A:   0
B update чужого (затронуто строк): 0
B delete чужого (затронуто строк): 0
B insert от имени A: row-level security policy for table …
anon читает: permission denied for table products
CHECK quantity<=0: violates check constraint …
дубль покупок: violates unique constraint …
A после атак B: 10.000
```
**Найденная проблема.** Первый прогон не поймал дубль «Творог»/«творог»: кластер был создан с локалью `C`, где `lower()` не приводит кириллицу к нижнему регистру. После `initdb --locale=C.UTF-8` проверка проходит. Вывод: БД должна иметь UTF-8 локаль (в Supabase это по умолчанию).

## 7. Обработка ошибок и логирование

| Ситуация | Сервер | Что видит пользователь |
|---|---|---|
| Ошибка валидации | 422 + ошибки по полям | Сообщение под полем формы |
| Нет токена, токен истёк или подделан | 401 | Экран входа: «Сессия истекла, войдите снова» |
| Чужая запись | 403 | «Нет доступа к этой записи» |
| Дубль | 409 | «Уже в списке» |
| Перебор паролей | 429 + `Retry-After` | «Слишком много попыток. Повторите через минуту» |
| Внутренняя ошибка | 500, подробности только в логе | «Ошибка сервера. Попробуйте позже» |
| Нет сети | — | Экран ошибки «Нет соединения…» и кнопка «Повторить» |

Журнал: одна JSON-строка на запрос (`ts`, `level`, `reqId`, `method`, `path`, `status`, `ms`, `userId`); `reqId` совпадает с заголовком ответа `X-Request-Id`. Уровни: 2xx и 3xx это `info`, 4xx это `warn`, 5xx это `error` с трассировкой.

### Анализ логов (пример реальной отладки)
При подготовке примеров запросов часть вызовов вернула 404 «Маршрут не найден». Фрагмент журнала:
```
{"ts":"2026-10-16T18:17:44.443Z","level":"warn","msg":"request","reqId":"8802ecf2","method":"POST","path":"/api/auth/register","status":422,"ms":10}
…
{"ts":"2026-10-16T18:17:44.539Z","level":"warn","msg":"request","reqId":"f351fc18","method":"POST","path":"/api/products/cc6dacee-449d-402d-a5ca-8c72d5fbb77b/consume","status":422,"ms":1,"userId":"387…
{"ts":"2026-10-16T18:17:44.540Z","level":"warn","msg":"request","reqId":"f6b7e489","method":"GET","path":"/api/products","status":401,"ms":0}
…
```
Сразу видно, что путь `/api/products//consume` содержит пустой id между слэшами. Значит, ошибка не на сервере, а в моём скрипте: переменная с id продукта оказалась пустой, потому что предыдущий запрос вернул 401 (в нём остался литерал `$TOKEN` вместо токена). После исправления скрипта все запросы прошли. Этот разбор сделан по логам: статус 401 у предыдущего запроса и «двойной слэш» в пути.

## 8. Тестирование

`npm test` запускает 32 теста (`node:test`):
- **API (15):** регистрация и вход, 401, CRUD, валидация 422, частичное списание (10 − 2 = 8; 200 г из 1 кг), изоляция пользователей (403), список покупок и дубли (409), CORS, некорректный JSON, 429, 500 без утечки деталей, отсутствие паролей в логах, статика и выход за каталог.
- **Фронтенд (17):** доменная логика, компоненты и XSS, клиент API (нет сети, 500 с HTML-ответом, 401, 403, 429, 422 по полям).

Сквозная проверка в браузере (Chromium через Playwright, мобильная и десктопная ширина): регистрация с ошибками валидации, добавление продуктов, списание (яйца 10 → 8, рис 1 кг − 250 г = 0,75 кг), данные сохраняются после перезагрузки (загружаются с сервера), дубль в покупках, обрыв сети с повтором, ответ 500, битый токен, неверный пароль. Ошибок JavaScript в консоли нет. Скриншоты: `screenshots/`.

**Найденные и исправленные проблемы в ходе разработки**
| Проблема | Как найдена | Решение |
|---|---|---|
| При правке тестов потерялся импорт, 3 теста упали | Запуск `npm test` | Импорт возвращён, 32 из 32 |
| Дубль по кириллице в PostgreSQL | Скрипт `test_rls.sh` | UTF-8 локаль (п. 6) |
| «Сетевая ошибка» не воспроизводилась в моём e2e-скрипте | Таймаут ожидания | Переход по `#` не перезагружает страницу; в скрипте добавлена перезагрузка (ошибка была в тесте, не в приложении) |
| Ложное «Сессия истекла» после неверного пароля | Вывод e2e-скрипта | Скрипт читал текст до обновления страницы; перепроверка с ожиданием нужного текста показала верное «Неверный email или пароль» |

## 9. Процесс разработки с AI
1. **Проектирование БД:** требования из ТЗ и user stories → схема, затем ручная доработка ограничений (п. 2).
2. **Генерация кода:** маршруты, аутентификация, миграции и клиент API генерировались по описанию эндпоинтов и правилам из `CLAUDE.md` (ДЗ 2); шаблоны RTCF использованы для тестов и интеграции.
3. **Отладка:** анализ логов и вывода тестов (п. 7, п. 8); каждая найденная проблема воспроизводилась тестом или скриптом.
4. **Ограничение:** проект подготовлен и проверен одним агентом в изолированной среде без Docker и npm; развёртывание на VPS или в Supabase и проверка на реальном устройстве остаются за вами.
