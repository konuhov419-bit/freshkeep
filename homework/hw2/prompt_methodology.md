# prompt_methodology.md — цепочка промптов (Chain-of-Thought)

## Выбранная задача

**«Ежедневный дайджест push-напоминаний о сроках годности»** (FR-3.1–FR-3.6, US-06 из ДЗ 3).

Почему задача сложная: нужно одновременно учесть правила отбора продуктов (срок, статус, удаление), защиту от дублей, настройки пользователя, группировку в одно сообщение и работу с датами без ошибок на границах (сегодня, часовой пояс, время суток). Если попросить «сделай уведомления» одним промптом, агент пропустит часть требований или придумает собственные.

## Техника

**Chain-of-Thought (цепочка рассуждений через декомпозицию):** задача разбита на 5 последовательных шагов. Каждый шаг — отдельный промпт по структуре RTCF; результат предыдущего шага вставляется в контекст следующего. Агент сначала рассуждает (анализ, проектирование), потом пишет код, потом проверяет себя.

```
Шаг 1: Анализ требований → Шаг 2: Проектирование → Шаг 3: Реализация → Шаг 4: Тесты и запуск → Шаг 5: Самопроверка
```

**Как выполнено.** Шаги выполнены последовательно в одной сессии агента Claude в рабочей среде: код и тесты записаны в `cot_demo/`, тесты реально запущены командой `npm test`. Честная оговорка: промпты ниже — сжатая формулировка того, что было задано на каждом шаге (без повторения правил из `rules.md`), а результаты шагов 1, 2 и 5 — это рассуждения агента, оформленные в таблицы; отдельные сырые логи каждого шага не сохранялись. Проверяемые артефакты — код, тесты и вывод запуска.

---

## Шаг 1. Анализ требований и граничных случаев

**Цель шага:** убедиться, что требования поняты правильно, до проектирования.

**Промпт**

```markdown
## Role
Ты — системный аналитик, который находит неоднозначности и граничные случаи.

## Task
Проанализируй требования FR-3.1–FR-3.6 и составь список правил отбора продуктов для дайджеста, а также граничные случаи и неоднозначности. Код не пиши.

## Context
FR-3.1: уведомлять о продуктах, где expires_at − today ≤ days_before.
FR-3.2: продукты объединяются в одно push-сообщение.
FR-3.3: настройки — за 1/2/3/5 дней, включено/выключено.
FR-3.4: не уведомлять об удалённых, съеденных, выброшенных.
FR-3.6: повторно по одному продукту — не чаще раза в сутки.

## Format
Таблица «Правило → Источник → Граничные случаи» и список вопросов по неоднозначностям.
```

**Результат**

| Правило | Источник | Граничные случаи |
|---|---|---|
| Включать продукт, если дней до срока ≤ `daysBefore` | FR-3.1 | Ровно `daysBefore` дней (включается); срок сегодня (0 дней); срок прошёл (отрицательное значение) |
| Исключать не активные и удалённые | FR-3.4 | Статусы `consumed`, `discarded`, флаг удаления |
| Исключать продукты, о которых уже уведомляли сегодня | FR-3.6 | Уведомление вчера (не исключается); время суток не влияет |
| Одно сообщение на пользователя | FR-3.2 | Много продуктов (текст нужно сократить); пустой набор (сообщения нет) |
| Выключенные уведомления | FR-3.3 | Нет сообщения даже при просроченных продуктах |
| Продукт без срока | FR-2.1 | Никогда не попадает в дайджест |

Неоднозначности и принятые решения:
1. **Попадают ли уже просроченные продукты?** Формула FR-3.1 (≤) их включает; принято решение: да, включаются.
2. **Как считать «дни до срока»?** Только по календарной дате, без времени суток.
3. **Где хранится «когда уведомляли»?** Вне задачи: функция принимает поле `lastNotifiedOn`, запись ведёт вызывающий сервис.

## Шаг 2. Проектирование типов и сигнатуры

**Промпт**

```markdown
## Role
Ты — Senior TypeScript-архитектор.

## Task
На основе результатов шага 1 спроектируй типы и сигнатуру чистой функции формирования дайджеста. Код реализации не пиши.

## Context
- Результат шага 1: <вставить таблицу правил и принятые решения>
- Архитектура: чистая логика в src/domain, текущее время передаётся параметром, без any.

## Format
TypeScript-интерфейсы и сигнатура функции с JSDoc, затем 3–5 пунктов «почему так».
```

**Результат (фрагмент)**

```ts
export interface DigestProduct {
  id: string; name: string;
  expiresAt: string | null;       // «ГГГГ-ММ-ДД»
  status: 'active' | 'consumed' | 'discarded';
  isDeleted: boolean;
  lastNotifiedOn: string | null;  // «ГГГГ-ММ-ДД»
}
export interface NotificationSettings { isEnabled: boolean; daysBefore: number }
export interface Digest { title: string; body: string; productIds: string[] }
export function buildDailyDigest(
  products: readonly DigestProduct[], settings: NotificationSettings, today: Date,
): Digest | null;
```

Обоснование: даты передаются строкой `ГГГГ-ММ-ДД`, поэтому нет влияния часовых поясов; `null` вместо пустого дайджеста упрощает вызывающий код; `today` параметром делает функцию тестируемой.

## Шаг 3. Реализация

**Промпт**

```markdown
## Role
Ты — Senior TypeScript-разработчик.

## Task
Реализуй `buildDailyDigest` по типам из шага 2 и правилам из шага 1.

## Context
- Типы и сигнатура: <результат шага 2>
- Правила отбора и решения по неоднозначностям: <результат шага 1>
- Тело сообщения: названия продуктов через запятую, максимум 3, далее «и ещё N». Сортировка: сначала самые срочные.

## Format
Один файл `src/daily-digest.ts` с JSDoc, ссылками на FR-* в комментариях, без any.
```

**Результат:** файл `cot_demo/src/daily-digest.ts` (около 80 строк). Конвейер отбора: фильтр по статусу и удалению → фильтр по `lastNotifiedOn` → расчёт дней → фильтр по `daysBefore` → сортировка → сборка сообщения.

## Шаг 4. Тесты и запуск

**Промпт**

```markdown
## Role
Ты — QA Automation инженер.

## Task
Напиши тесты для `buildDailyDigest` по каждому правилу FR-3.x и граничным случаям из шага 1 и запусти их.

## Context
- Код: <src/daily-digest.ts>
- Таблица правил и граничных случаев: <результат шага 1>
- Фреймворк: node:test; текущая дата фиксируется параметром.

## Format
Файл `test/daily-digest.test.ts`, название теста содержит номер требования, затем вывод запуска.
```

**Результат:** файл `cot_demo/test/daily-digest.test.ts`, **12 тестов, 12 пройдено, 0 упало** (`npm test`). Покрыто: граница `daysBefore`, просроченные, объединение и сокращение текста, исключение удалённых/съеденных/выброшенных, защита от дублей, выключенные уведомления, пустой набор и продукты без срока, сортировка, независимость от времени суток, некорректная дата. Дополнительно код проверен командой `tsc --strict` (ошибок нет), поиск `any` и `@ts-ignore` ничего не нашёл.

## Шаг 5. Самопроверка по требованиям

**Промпт**

```markdown
## Role
Ты — ревьюер, проверяющий соответствие кода требованиям.

## Task
Сопоставь реализацию с FR-3.1–FR-3.6 и укажи, какие требования закрыты, какие нет и какие допущения остались.

## Context
<вставить код, тесты и таблицу из шага 1>

## Format
Таблица «Требование → Закрыто? → Где проверено (тест)» и список допущений.
```

**Результат**

| Требование | Закрыто? | Где проверено |
|---|---|---|
| FR-3.1 отбор по сроку | Да | тесты «в пределах», «граница», «просроченные» |
| FR-3.2 одно сообщение | Да | «объединяются», «тело сокращается» |
| FR-3.3 настройки | Частично: `isEnabled` и `daysBefore` учитываются; время рассылки (09:00) вне функции, это забота планировщика | «выключенные уведомления» |
| FR-3.4 исключения | Да | «удалённые, съеденные, выброшенные» |
| FR-3.5 баннер при запрещённых уведомлениях | Нет: относится к клиенту, не к этой функции | — |
| FR-3.6 не чаще раза в сутки | Да (по полю `lastNotifiedOn`; запись поля делает вызывающий код) | «уже уведомляли сегодня» |

Остаточные допущения: просроченные продукты включаются; часовой пояс пользователя учитывает вызывающий код при создании `today`; повторные напоминания о просроченном продукте будут приходить ежедневно, пока его не удалят или не отметят съеденным (стоит уточнить, нужно ли это).

|---|---|
| Шагов в цепочке | 5 |
| Промптов | 5 (по одному на шаг) |
| Итераций исправления кода | 0: код и тесты прошли с первого запуска |
| Результат | 12 из 12 тестов, `tsc --strict` без ошибок |
| Что дала декомпозиция | Неоднозначности (просроченные продукты, расчёт дней, хранение `lastNotifiedOn`) выявлены до написания кода, а не при отладке; тесты привязаны к требованиям |
| Ограничения | Цепочка выполнена один раз одним агентом: это демонстрация техники, а не статистика. Шаги 1–2 стоило бы показать заказчику до реализации |
