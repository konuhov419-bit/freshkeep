# prompt_templates.md — библиотека промпт-шаблонов (RTCF)

Все шаблоны построены по структуре **RTCF**: **R**ole (роль) → **T**ask (задача) → **C**ontext (контекст) → **F**ormat (формат результата). В угловых скобках `<...>` — поля, которые нужно заполнить. Шаблоны рассчитаны на работу вместе с файлом `rules.md`: общие правила стека и стиля повторять в промпте не нужно.

Проект для примеров — FreshKeep (`hw_ai_rules.md`).

| № | Сценарий | Когда использовать |
|---|---|---|
| 1 | Генерация компонента/функции по описанию | Новая функциональность с понятным поведением |
| 2 | Рефакторинг с улучшением | Код работает, но сложно читать или поддерживать |
| 3 | Написание тестов | Есть код без тестов или нужно покрыть критерии приёмки |
| 4 | Исправление ошибок и багов | Есть воспроизводимая ошибка |
| 5 | Декомпозиция сложной задачи | Большая задача, которую нельзя сделать за один шаг |

---

## Шаблон 1. Генерация компонента или функции по описанию

```markdown
## Role
Ты — Senior <роль, например: React Native / NestJS> разработчик, который пишет код, готовый к code review.

## Task
Реализуй <функцию / компонент / сервис> «<название>», которая <что делает, 1–2 предложения>.

## Context
- Требования: <ссылки на FR-*, US-* из technical_specification.md / user_stories.md>
- Входные данные: <типы и примеры>
- Выходные данные: <типы и примеры>
- Граничные случаи и ошибки: <список>
- Где лежит код / что уже есть: <пути файлов, существующие типы>
- Ограничения: <производительность, библиотеки, чего избегать>

## Format
1. Краткий план (2–4 пункта).
2. Код с путём файла в заголовке блока.
3. Тесты (позитивные, негативные, граничные).
4. Команда запуска.
5. Допущения и открытые вопросы.
```

### Пример использования

```markdown
## Role
Ты — Senior TypeScript-разработчик (NestJS), который пишет код, готовый к code review.

## Task
Реализуй функцию `buildShoppingItemFromProduct`, которая при подтверждении «Закончился» создаёт позицию списка покупок из продукта инвентаря.

## Context
- Требования: FR-5.4, US-11 (дубликаты по нормализованному названию не создаются).
- Входные данные: `product: Product`, `existingItems: ShoppingItem[]`.
- Выходные данные: `ShoppingItem | null` (`null`, если такая позиция уже есть); `source: 'auto'`.
- Граничные случаи: название с разным регистром и лишними пробелами; пустой список.
- Где лежит код: `src/domain/shopping/`; типы в `src/domain/types.ts`.
- Ограничения: без обращения к БД, без `any`.

## Format
План, код с путём файла, тесты, команда запуска, допущения.
```

## Шаблон 2. Рефакторинг кода с улучшением

```markdown
## Role
Ты — Senior разработчик и ревьюер, специалист по читаемому и поддерживаемому коду.

## Task
Проведи рефакторинг приведённого кода. Цель: <читаемость / разбить длинную функцию / убрать дублирование / улучшить типы>. Поведение должно остаться прежним.

## Context
- Код для рефакторинга:
  ```<язык>
  <вставить код>
  ```
- Существующие тесты: <есть/нет, путь>
- Что нельзя менять: <публичный API, сигнатуры, формат ответов>
- Известные проблемы: <список>

## Format
1. Список найденных проблем (по приоритету).
2. Рефакторинг-версия кода.
3. Таблица «Было → Стало → Зачем».
4. Что проверить (тесты, которые должны остаться зелёными).
```

### Пример использования

```markdown
## Role
Ты — Senior TypeScript-разработчик и ревьюер.

## Task
Проведи рефакторинг функции `getFreshness`. Цель: убрать цепочку `.replace(...)` при формировании подписи «просрочено N дн.». Поведение остаётся прежним.

## Context
- Код:
  ```ts
  label: `просрочено ${pluralDays(daysLeft).replace("дней", "дн.").replace("дня", "дн.").replace("день", "дн.")}`
  ```
- Существующие тесты: `test/freshness.test.js`, 8 тестов.
- Что нельзя менять: сигнатуру `getFreshness(expiresAt, today)` и поля результата.

## Format
Проблемы, исправленный код, таблица «Было → Стало → Зачем», список тестов для проверки.
```

## Шаблон 3. Написание тестов для существующего кода

```markdown
## Role
Ты — инженер по тестированию (QA Automation), который пишет детерминированные, быстрые и понятные тесты.

## Task
Напиши тесты для <функции / модуля / компонента> «<название>», покрыв позитивные, негативные и граничные сценарии.

## Context
- Код:
  ```<язык>
  <вставить код или путь к файлу>
  ```
- Критерии приёмки (Given-When-Then): <вставить из user_stories.md>
- Тестовый фреймворк: <Jest / node:test>
- Что нельзя мокать / что нужно мокать: <список>
- Время: <фиксировать текущую дату параметром, не использовать реальные часы>

## Format
1. Таблица тест-кейсов: «Сценарий → Входные данные → Ожидаемый результат».
2. Файл с тестами (`*.test.ts`), названия тестов на русском в формате «когда … тогда …».
3. Команда запуска.
4. Какие случаи остались непокрытыми и почему.
```

### Пример использования

```markdown
## Role
Ты — QA Automation инженер.

## Task
Напиши тесты для функции `getFreshness`, покрыв позитивные, негативные и граничные сценарии.

## Context
- Код: `src/freshness.js` (функция `getFreshness(expiresAt, today)`).
- Критерии приёмки US-05: более 3 дней — green; 1–3 дня — orange; сегодня или просрочено — red; без срока — none.
- Фреймворк: встроенный `node:test`.
- Время: `today` передаётся параметром; время суток не должно влиять на результат.

## Format
Таблица тест-кейсов, файл `test/freshness.test.js`, команда `npm test`, список непокрытых случаев.
```

## Шаблон 4. Исправление ошибок и багов

```markdown
## Role
Ты — Senior разработчик, специалист по отладке: сначала находишь первопричину, потом чинишь.

## Task
Найди причину и исправь баг: <краткое описание проблемы>.

## Context
- Ожидаемое поведение: <что должно происходить>
- Фактическое поведение: <что происходит>
- Шаги воспроизведения: <1, 2, 3>
- Код:
  ```<язык>
  <вставить код>
  ```
- Сообщение об ошибке / стек: <вставить>
- Что уже пробовали: <список>
- Окружение: <версии, платформа>

## Format
1. Гипотезы причины (по вероятности) и как их проверить.
2. Найденная первопричина (1–2 предложения).
3. Минимальное исправление (diff или код).
4. Тест, который воспроизводит баг и проходит после исправления.
5. Как убедиться, что соседний функционал не сломан.
```

### Пример использования

```markdown
## Role
Ты — Senior TypeScript-разработчик, специалист по отладке.

## Task
Найди причину и исправь баг: напоминание приходит на день раньше для пользователей из часового пояса UTC+3.

## Context
- Ожидаемое поведение: продукт со сроком 20.10 попадает в уведомление «за 2 дня» 18.10 в 09:00 по местному времени.
- Фактическое поведение: уведомление приходит 17.10.
- Шаги: продукт со сроком 2026-10-20, часовой пояс Europe/Moscow, запуск джоба 18.10 в 09:00 MSK.
- Код: функция `daysUntil(expiresAt: Date, now: Date)` использует `Math.floor((expiresAt - now) / 86400000)`.
- Что уже пробовали: заменили `floor` на `round`, стало хуже для вечера.

## Format
Гипотезы, первопричина, исправление, тест-воспроизведение, проверка соседнего функционала.
```

## Шаблон 5. Декомпозиция сложной задачи на подзадачи

```markdown
## Role
Ты — технический лид и архитектор, который разбивает крупные задачи на небольшие независимые шаги, пригодные для передачи AI-агенту.

## Task
Разбей задачу «<название и цель задачи>» на подзадачи. Каждая подзадача — не более 1–2 часов работы и проверяется отдельно.

## Context
- Описание и требования: <FR-*, US-*, NFR-*>
- Текущее состояние проекта: <что уже есть>
- Ограничения: <сроки, стек, зависимости>
- Критерии готовности всей задачи: <Definition of Done>

## Format
Таблица подзадач: № | Название | Описание | Зависит от | Результат (артефакт) | Как проверить | Оценка.
После таблицы: критический путь, риски и вопросы, без которых нельзя начинать.
Не пиши код — только план.
```

### Пример использования

```markdown
## Role
Ты — технический лид и архитектор, который разбивает крупные задачи на независимые шаги для AI-агента.

## Task
Разбей задачу «Ежедневные push-напоминания о сроках годности» на подзадачи (каждая до 1–2 часов).

## Context
- Требования: FR-3.1–FR-3.6 (формирование уведомлений, объединение в одно сообщение, настройки, защита от дублей), US-06, US-07.
- Текущее состояние: модель `Product` и таблица `NotificationSettings` уже есть; push-токены пока не хранятся.
- Ограничения: NestJS, Firebase Cloud Messaging, cron-джоб раз в день.
- Критерии готовности: все критерии US-06 и US-07 проходят автотесты.

## Format
Таблица подзадач (№, название, описание, зависит от, результат, как проверить, оценка), затем критический путь и риски. Код не писать.
```

## Приложение: чек-лист хорошего промпта

- Роль конкретна (не «помощник», а «Senior NestJS-разработчик»).
- Задача формулируется одним глаголом и одной целью.
- В контексте есть ссылки на требования, типы и существующий код, а не только общие слова.
- Формат результата перечислен по пунктам; сказано, чего не делать.
- Одна задача — один промпт; сложное разбивается (шаблон 5, `prompt_methodology.md`).
