## 1. Описание проекта

### 1.1 Название и назначение
**FreshKeep** — мобильное приложение для учёта продуктов дома, контроля сроков годности и подбора рецептов из имеющихся продуктов.

### 1.2 Проблема
Домохозяйства выбрасывают продукты с истёкшим сроком, покупают дубли и тратят время на выбор блюда.

### 1.3 Цели и метрики
- ≥ 60% новых пользователей добавляют ≥ 10 продуктов за первую неделю.
- D7 retention ≥ 30%.
- Время добавления продукта по штрихкоду ≤ 15 секунд.

### 1.4 Вне MVP
Распознавание чеков, интеграции с магазинами, подсчёт КБЖУ, социальные функции, платные подписки.

### 1.5 Рекомендуемый технический стек
| Слой | Технология |
|---|---|
| Клиент | React Native (Expo) + TypeScript, либо PWA (React + Vite) |
| Бэкенд | Node.js (NestJS) + REST API (JSON), OpenAPI 3.0 |
| БД | PostgreSQL |
| Аутентификация | JWT (access 15 мин + refresh 30 дней) |
| Push | Firebase Cloud Messaging |
| Штрихкоды | Open Food Facts API (+ локальный кэш) |
| Рецепты | Собственная БД рецептов (seed ≥ 200 рецептов) |
| Тесты | Jest, Playwright/Detox |

## 4. Функциональные требования

### FR-1. Аккаунт и аутентификация (US-01, US-15)
| ID | Требование |
|---|---|
| FR-1.1 | Регистрация по email + паролю (≥ 8 символов, хотя бы 1 буква и 1 цифра). |
| FR-1.2 | Вход по email + паролю; выдача JWT access/refresh. |
| FR-1.3 | При регистрации автоматически создаётся Household, пользователь — owner. |
| FR-1.4 | Выход: refresh-токен инвалидируется. |
| FR-1.5 | (Nice) Вход через Google OAuth. |

**API:** `POST /auth/register`, `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout`.

**Приёмка:** критерии US-01.

### FR-2. Инвентарь продуктов (US-02, US-03, US-04, US-05, US-13, US-14)
| ID | Требование |
|---|---|
| FR-2.1 | Создание продукта: название (1–100 символов, обязательно), количество (> 0, обязательно), единица, место хранения (по умолчанию «Холодильник»), срок годности (необязательно). |
| FR-2.2 | Быстрые сроки в форме: «+3 дня», «+7 дней», «+14 дней», «+30 дней», календарь. |
| FR-2.3 | Кнопка «Добавить ещё» очищает форму, сохраняя место хранения. |
| FR-2.4 | Сканирование штрихкода камерой (EAN-13/EAN-8/UPC-A); название подставляется из Open Food Facts за ≤ 3 с. |
| FR-2.5 | Редактирование всех полей продукта; удаление свайпом с undo 5 секунд (soft delete). |
| FR-2.6 | Главный экран: сетка карточек 2 колонки; сортировка по сроку (ближайшие первыми); чипы фильтра по месту хранения. |
| FR-2.7 | Индикация свежести: зелёный (> 3 дней), оранжевый (1–3 дня), красный (≤ 0 или просрочено), серый (нет срока); подпись текстом дублирует цвет. |
| FR-2.8 | Действия над продуктом: «съедено» / «выброшено» (меняет status, фиксируется для статистики). |
| FR-2.9 | (Should) Поиск по названию (регистронезависимый, подстрока), режим компактного списка. |
| FR-2.10 | (Nice) Подсказки популярных продуктов с типичным сроком. |

**API:** `GET/POST /products`, `GET/PATCH/DELETE /products/{id}`, `GET /barcodes/{code}`.

**Приёмка:** критерии US-02–05, US-13, US-14.

### FR-3. Напоминания (US-06, US-07)
| ID | Требование |
|---|---|
| FR-3.1 | Ежедневный cron-джоб формирует push для продуктов, у которых `expires_at − today ≤ days_before`. |
| FR-3.2 | Продукты объединяются в одно push-сообщение на пользователя в день. |
| FR-3.3 | Настройки: «за 1/2/3/5 дней», время (по умолчанию 09:00 в часовом поясе пользователя), включение/выключение. |
| FR-3.4 | Уведомление не отправляется для удалённых, съеденных, выброшенных продуктов. |
| FR-3.5 | При запрещённых системных уведомлениях показывается баннер с предложением включить (не блокирует работу). |
| FR-3.6 | Повторное уведомление по одному и тому же продукту — не чаще 1 раза в сутки. |

**API:** `GET/PUT /notification-settings`, `POST /devices` (регистрация push-токена).

**Приёмка:** критерии US-06, US-07.

### FR-4. Рецепты (US-08, US-09, US-16)
| ID | Требование |
|---|---|
| FR-4.1 | Подбор: рецепт ранжируется по доле совпавших ингредиентов (сопоставление по нормализованному названию), затем по числу ингредиентов с ближайшим сроком. |
| FR-4.2 | Показывается только рецепты с ≥ 50% совпадений. |
| FR-4.3 | Карточка рецепта: название, время, «Есть N из M ингредиентов», недостающие ингредиенты, шаги. |
| FR-4.4 | Кнопка «Добавить недостающее в покупки». |
| FR-4.5 | Кнопка «Готовлю»: списывает использованные продукты (диалог подтверждения количества). |
| FR-4.6 | Баннер на главной: лучший рецепт для продуктов, истекающих ≤ 3 дней. Скрывается при отсутствии таких продуктов. |
| FR-4.7 | (Should) Фильтры: время приготовления (≤ 20 / ≤ 40 мин), диета (вегетарианское, без глютена, без лактозы). |
| FR-4.8 | (Nice) Избранные рецепты. |
| FR-4.9 | Минимум 3 продукта в инвентаре для показа рецептов, иначе пустое состояние. |

**API:** `GET /recipes?time_max=&diet=`, `GET /recipes/{id}`, `POST /recipes/{id}/cook`.

**Приёмка:** критерии US-08, US-09, US-16.

### FR-5. Список покупок (US-10, US-11)
| ID | Требование |
|---|---|
| FR-5.1 | Добавление позиции (название обязательно, количество необязательно); дубликаты по нормализованному названию запрещены. |
| FR-5.2 | Отметка «куплено» → предложение перенести в инвентарь (открывается форма с предзаполненным названием). |
| FR-5.3 | Удаление позиции (undo 5 с). |
| FR-5.4 | При подтверждении «закончился» продукт добавляется в список покупок с `source=auto`; дубликаты не создаются. |

**API:** `GET/POST /shopping-items`, `PATCH/DELETE /shopping-items/{id}`.

**Приёмка:** критерии US-10, US-11.

### FR-6. Семейный доступ (US-12)
| ID | Требование |
|---|---|
| FR-6.1 | Owner создаёт ссылку-приглашение (срок действия 7 дней, одноразовая). |
| FR-6.2 | Принявший приглашение получает доступ к общему инвентарю и списку покупок. |
| FR-6.3 | Изменения одного участника видны другим в течение 5 секунд (polling каждые 5 с или WebSocket). |
| FR-6.4 | Только owner может удалять участников и приглашать. |
| FR-6.5 | Максимум 6 участников на Household. |
| FR-6.6 | Пользователь видит только данные своего Household (проверка на сервере в каждом запросе). |

**API:** `POST /household/invitations`, `POST /invitations/{token}/accept`, `GET /household/members`, `DELETE /household/members/{userId}`.

**Приёмка:** критерии US-12.

## 6. Обработка ошибок

### 6.1 Общий формат ответа API при ошибке
```json
{ "error": { "code": "VALIDATION_ERROR", "message": "Укажите название", "field": "name" } }
```

### 6.2 Требования

| ID | Тип | Условие | HTTP | Поведение клиента (UX) |
|---|---|---|---|---|
| ERR-1 | Валидация | Обязательное поле пустое / неверный формат | 400 | Inline-сообщение под полем, красная рамка, фокус на первое ошибочное поле; данные формы сохраняются |
| ERR-2 | Валидация | Количество ≤ 0 или не число | 400 | «Количество должно быть больше 0» |
| ERR-3 | Валидация | Срок в прошлом | — (клиентская проверка) | Диалог «Добавить как просроченный / Изменить дату» |
| ERR-4 | Валидация | Дубликат email / позиции покупок | 409 | «Этот email уже используется. Войти?» / «Уже в списке» |
| ERR-5 | Нет данных | Пустой инвентарь / покупки / рецепты / поиск | 200 (пустой массив) | Пустое состояние с иллюстрацией и главным действием (CTA) |
| ERR-6 | Нет данных | Штрихкод не найден | 404 | «Продукт не найден. Введите данные вручную», штрихкод сохраняется в форме |
| ERR-7 | Сеть | Нет соединения | — | Баннер «Нет соединения»; чтение из кэша; запись в очередь, отправка при появлении сети |
| ERR-8 | Сеть | Таймаут (> 10 с) или 5xx | 5xx | Снекбар «Что-то пошло не так. Повторить»; автоповтор до 3 раз с экспоненциальной задержкой; данные не теряются |
| ERR-9 | Сеть | Конфликт одновременного редактирования | 409 | Применяется последнее изменение; тост «Продукт был обновлён <имя>» |
| ERR-10 | Доступ | Access-токен истёк | 401 | Тихий refresh токена и повтор запроса; при неудаче — экран входа и возврат на прежний экран после входа |
| ERR-11 | Доступ | Нет прав на ресурс / чужой Household | 403 | Экран «У вас нет доступа» + «На главную»; событие логируется |
| ERR-12 | Доступ | Приглашение просрочено / уже использовано | 410 | «Приглашение устарело. Попросите новое» |
| ERR-13 | Доступ | Превышен rate-limit | 429 | «Слишком много попыток. Повторите через N секунд», кнопка заблокирована на время ожидания |
| ERR-14 | Разрешения | Доступ к камере запрещён | — | Экран с пояснением, «Открыть настройки», «Ввести вручную» |
| ERR-15 | Разрешения | Push запрещены | — | Баннер «Включите уведомления» (не блокирует работу) |

### 6.3 Общие принципы
1. Не терять введённые пользователем данные.
2. Каждое сообщение объясняет, что случилось и что делать дальше.
3. Не показывать технические детали (стек, SQL, коды) пользователю.
4. Деструктивные действия обратимы (undo 5 с).
5. Все ошибки сервера логируются с request-id.
