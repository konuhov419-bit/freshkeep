# Отчёт по аудиту безопасности FreshKeep (ДЗ 6)

Объект: код после ДЗ 5 (v2) → исправленная версия v3.0.0. Метод: проверка зависимостей, ручной обзор по OWASP Top 10 (2021) с участием AI-агента (Claude), затем **тесты-«красные»**: для каждой гипотезы уязвимости сначала написан тест, который падает на старом коде, потом исправление. Базовый прогон старого кода: 24 из 64 тестов падали (список в `docs/.baseline.txt`), после исправлений проходят все 70.

## 1. Зависимости

Проект не использует сторонних пакетов (только встроенные модули Node.js 22), поэтому цепочка поставок минимальна. `npm audit --omit=dev --audit-level=low` → **0 уязвимостей**; команда выполняется в CI на каждый пуш. Файл `package-lock.json` добавлен, чтобы `npm audit` и `npm ci` работали. Dependabot (`.github/dependabot.yml`) еженедельно проверяет GitHub Actions, Docker-образ и npm.

## 3. Защита от распространённых атак

- **SQL-инъекции.** Все запросы параметризованы (`?` в `node:sqlite`), конкатенации SQL нет. Тест отправляет классические нагрузки (`'; DROP TABLE …`) → они сохраняются как обычный текст, таблицы целы.
- **XSS.** Весь пользовательский ввод экранируется функцией `esc` при построении HTML; `innerHTML` с неэкранированными данными запрещён правилом `CLAUDE.md` и линтером; CSP запрещает inline-скрипты, так что даже пропущенная вставка не выполнится.
- **CSRF.** Проверка `Origin` + токен не в cookie. Единственная cookie (`fk_oauth`) — служебная для OAuth: подписанная, `HttpOnly`, `SameSite=Lax`, живёт 10 минут.
- **OAuth.** Authorization Code + **PKCE (S256)**, `state` привязан к cookie, ошибки возвращаются во фрагменте URL (не попадают в логи и Referer), одноразовый тикет на 60 секунд вместо токена в адресе.
- **JWT.** Принимается только HS256; `alg=none` и чужая подпись отклоняются; секрет не короче 32 символов (иначе предупреждение `config.warning`).

## 4. Проверка по OWASP Top 10 (2021)

| Категория | Статус | Комментарий |
|---|---|---|
| A01 Broken Access Control | Исправлено | Изоляция данных по `user_id` (403 на чужие записи), CSRF, отзыв токенов |
| A02 Cryptographic Failures | Исправлено | scrypt для паролей, HS256 с длинным секретом, HSTS, Secure-cookie при https |
| A03 Injection | Исправлено | Параметризованные SQL, экранирование HTML, CSP |
| A04 Insecure Design | Частично | Квоты, валидация, лимиты. Нет подтверждения email при самостоятельной регистрации (см. рекомендации) |
| A05 Security Misconfiguration | Исправлено | Заголовки, `no-store`, TRUST_PROXY, отсутствие стека в ответах 500 |
| A06 Vulnerable Components | Нет рисков | Зависимостей нет; `npm audit` в CI; Dependabot |
| A07 Identification & Authentication Failures | Исправлено | Блокировка, выравнивание времени, отзыв токенов, OAuth с PKCE |
| A08 Software & Data Integrity | Частично | Подписанные токены и cookie; CI закреплён на мажорных версиях Actions (рекомендация: закрепить SHA) |
| A09 Logging & Monitoring Failures | Исправлено | JSON-логи, маскирование, метрики, health/ready, uptime-проба |

## 5. Как использовался AI

1. Агент прочитал исходники и составил гипотезы по категориям OWASP (запрос: «проанализируй server/app.js по OWASP Top 10, перечисли конкретные места и сценарии атаки, не предлагай общих советов»).
2. По каждой гипотезе агент написал падающий тест; результат прогона зафиксирован (`docs/.baseline.txt`).
3. Исправления проверены повторным прогоном и сквозным тестом в браузере (Playwright): вход через OAuth, отказ, отзыв токена, CSP без нарушений.
4. Вердикты агента проверены человеком по тестам: гипотезы, не подтвердившиеся тестом, в отчёт не включены.

## 6. Ограничения и честные оговорки

- Аудит проводился в изолированной среде без доступа к сети и к реальным провайдерам OAuth: обмен кода проверен на поддельном провайдере (`scripts/mock-oauth.js`), а не на Google/Яндекс.
- Внешний сканер (OWASP ZAP, Burp) не запускался; CodeQL подключён в `.github/workflows/codeql.yml` и сработает после пуша в GitHub.
- Файл SQLite и логи лежат на диске контейнера: на хостинге нужен постоянный том.

## 7. Рекомендации

1. Подтверждение email при самостоятельной регистрации (письмо со ссылкой), после этого можно снять часть ограничений привязки.
2. Хранить токен в `HttpOnly`-cookie с `SameSite=Strict` вместо `localStorage` (защита от кражи токена при XSS), добавив CSRF-токен.
3. Двухфакторная аутентификация (TOTP).
4. Ротация `JWT_SECRET` (поддержка двух ключей на время перехода).
5. Закрепить GitHub Actions по SHA коммита, включить branch protection для `main` и обязательные проверки.
6. Переход на PostgreSQL (схема с RLS есть в `supabase/`) при росте нагрузки: SQLite рассчитан на один экземпляр.
7. Внешнее хранилище логов и алерты (Better Stack, Grafana Loki).
